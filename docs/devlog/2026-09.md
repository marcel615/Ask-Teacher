## 2026-09-15 - Issue #32 API 공통 응답 타입 개선

- Issue URL: https://github.com/marcel615/Ask-Teacher/issues/32
- PR: #35 refactor: 성공 API 응답에서 공통 래퍼 제거 (#32)
- PR URL: https://github.com/marcel615/Ask-Teacher/pull/35
- PR 상태: OPEN
- Branch: `feature/issue-32-api-response-refactor` → `develop`

### 오늘의 작업

- 인증·게시글·카테고리·게시글 좋아요 API의 성공 응답에서 `ApiResponse<T>` 래퍼를 제거했다.
- 후속 승인에 따라 자동 테스트를 실행하고, 변경 API의 `.http` 예시를 갱신한 뒤 수동 API를 확인했다.
- 변경된 성공 응답 형식을 `docs/api-spec.md`에 반영했다.

### 변경 내용

- 데이터가 있는 성공 응답은 기존 DTO 또는 목록을 `ResponseEntity` 본문에 직접 반환한다.
- 회원가입·게시글 작성은 201, 로그인·카테고리 조회·게시글 조회 및 수정은 200을 유지한다.
- 좋아요 등록은 200, 좋아요 취소·게시글 삭제는 204를 반환하며 세 응답 모두 본문이 없다.
- 미사용 `ApiResponse.java`를 별도 승인 후 삭제했다.
- 기존 `.http` 파일의 `response.body.data` 참조와 오래된 게시글 작성 요청 형식을 변경된 API에 맞게 갱신했다.

### 테스트 결과 / 수동 확인 결과

- `./gradlew test`: `BUILD SUCCESSFUL`. `ApiResponse.java` 삭제 후에도 재실행해 통과했다.
- 로컬 18080 포트에서 PowerShell·curl로 수동 확인했다. 회원가입·게시글 작성은 201, 로그인·카테고리·게시글 목록/상세/수정은 200이며 DTO 또는 목록이 본문에 직접 반환됐다.
- 좋아요 등록은 200, 좋아요 취소·게시글 삭제는 204였고 세 응답의 본문은 비어 있었다.
- 컨트롤러와 `.http` 파일에 `ApiResponse` 및 `response.body.data` 사용이 남아 있지 않은지 `rg`로 확인했다.
- `.http` 파일은 갱신했으며, 기록된 수동 요청 실행 방법은 PowerShell·curl이다.

### 문제 / 해결

- 첫 테스트 실행에서 sandbox 네트워크 제한으로 Gradle 배포 파일을 받지 못했다. 허용된 환경에서 다시 실행해 통과를 확인했다.
- 수동 확인용 `bootRun`은 기본 포트 8080이 사용 중이라 시작하지 못했다. 로컬 18080 포트로 실행했다.
- PowerShell 5의 `Invoke-WebRequest`가 기본 IE 파서 문제로 응답을 읽지 못했다. `-UseBasicParsing` 옵션으로 재시도했다.
- 응답 상태 코드는 `ResponseEntity`에서 직접 지정하고 `@ResponseStatus`를 제거하기로 했다.
- 처음에는 미사용 `ApiResponse.java`가 남아 있었다. 삭제 여부를 별도로 승인받은 뒤 삭제하고 테스트를 재실행했다.

## 2026-09-16 - Issue #33 전체 API 자동 테스트 구축 및 수동 테스트 지침 전환

### Issue / PR

- Issue: #33 test: 전체 API 자동 테스트 구축 및 수동 테스트 지침 전환
- Issue URL: https://github.com/marcel615/Ask-Teacher/issues/33
- PR: #36 test: 전체 API 자동 테스트 구축 및 인증 응답 검증
- PR URL: https://github.com/marcel615/Ask-Teacher/pull/36
- PR 상태: OPEN
- Branch: `feature/issue-33-api-automated-tests` → `develop`

### 오늘의 작업

- 인증·카테고리·게시글·좋아요 API의 Controller, Service, Repository 및 통합 테스트를 작성하거나 보완했다.
- 기존 `.http` 파일의 시나리오를 자동 테스트로 전환하고 관련 파일 9개를 삭제했다.
- 테스트 전용 DB·JWT·파일 저장 환경을 구성하고 반복 실행 시 데이터와 파일이 남지 않도록 정리 방식을 적용했다.
- 테스트에서 발견된 미인증 응답의 명세 불일치를 승인된 범위에서 수정하고 관련 회귀 테스트를 강화했다.
- 작업 지침, 리뷰 기준, Issue·PR 템플릿과 README의 수동 API 확인 안내를 자동 테스트 기준으로 변경했다.

### 변경 내용

- Controller 테스트에서 요청 바인딩, Validation과 경계값, 응답 상태·본문 및 예외 응답을 검증했다.
- Service 테스트에서 인증, 게시글, 카테고리와 좋아요의 비즈니스 규칙 및 주요 실패 조건을 검증했다.
- Repository 테스트에서 H2 테스트 DB를 이용해 실제 저장·조회·수정·삭제, 사용자 정의 쿼리, 매핑과 관련 제약조건을 검증했다.
- `ApiIntegrationTest`에서 실제 Security·Service·Repository를 연결해 인증부터 DB 처리까지 API의 정상·주요 실패 흐름을 검증했다.
- 파일 저장 동작과 실제 HTTP 환경의 10MB 업로드 경계 및 초과 요청을 자동 테스트로 검증했다.
- 기존 DB 기반 `PostServiceTest` 시나리오 13개를 `PostServiceIntegrationTest`로 이동해 보존하고, `PostServiceTest`는 mock 기반 단위 테스트로 분리했다.
- 보호 API에서 토큰이 없거나 유효하지 않을 때 정확한 401 상태와 `{"status":401,"message":"인증이 필요합니다."}` JSON 응답을 반환하도록 `SecurityConfig`와 `ErrorCode`를 변경했다.
- JWT 발급·검증, 접근 허용 규칙 및 인증된 사용자의 작성자 불일치 403 정책은 변경하지 않았다.

### 자동 테스트 범위 / 실행 결과 / 미검증 사항

- 범위: 인증·카테고리·게시글·좋아요 API의 Controller, Service, Repository와 API 통합 흐름
- 추가 범위: 파일 저장, JWT 유효성·만료·잘못된 서명, 미인증 응답, 실제 HTTP 업로드 크기 제한, 테스트 데이터·파일 정리
- `.\gradlew.bat test`: 105개 실행, 실패 0, skip 0, `BUILD SUCCESSFUL`
- `.\gradlew.bat test --rerun-tasks`: 105개 재실행, 실패 0, skip 0, `BUILD SUCCESSFUL`
- `git diff --check`: 통과
- 반복 실행에서 데이터 또는 파일 잔존으로 인한 추가 실패가 발생하지 않았다.
- 기존 수동 API 확인은 실행하지 않았으며, 실제 HTTP 검증이 필요한 인증 응답과 업로드 제한은 RANDOM_PORT 기반 자동 테스트로 확인했다.
- H2 기반 테스트는 MySQL 고유 동작과 성능·부하·동시성 특성을 검증하지 않는다.
- 삭제된 게시글의 수정 허용 여부는 현재 명세에 정책이 명확하지 않아 검증 및 운영 코드 변경 대상에서 제외했다.
- CI 파이프라인 검증은 이번 Issue 범위에 포함하지 않았다.

### 문제 / 해결

- 최초 Gradle 실행이 sandbox 네트워크 제한으로 실패했다. 허용된 환경에서 다시 실행해 전체 테스트 결과를 확인했다.
- 계층 테스트 첫 실행에서는 매개변수 테스트의 배열 인자 전달 오류로 84개 중 6개가 실패했다. 테스트 인자를 개별 필드로 전달하도록 수정했다.
- 이후 전체 실행에서는 보호 API의 토큰 누락·무효 토큰 요청이 명세의 401이 아닌 403을 반환해 104개 중 10개가 실패했다. 기대값 완화나 테스트 비활성화 없이 사용자와 처리 방향을 협의했다.
- 승인 후 `AuthenticationEntryPoint`와 `UNAUTHORIZED` 오류 코드를 추가하고, 보호 API 5개에 대한 토큰 누락·무효 토큰 10개 시나리오에서 401, JSON 본문, Content-Type과 UTF-8을 검증했다.
- 인증 응답 수정 후 전체 테스트 105개와 반복 실행이 모두 통과했다. 공개 API, 로그인 실패 및 인증된 비작성자의 403 동작도 유지됨을 확인했다.
- 삭제된 게시글 수정은 현재 구현에서 삭제 여부를 확인하지 않지만 관련 정책이 명시되지 않았다. 이번 범위에서는 변경하지 않고 후속 검토 후보로 남겼다.
