## 목표와 범위

- 게시글 생성 `POST /api/posts` 및 수정 `PATCH /api/posts/{postId}`의 첨부파일 저장 또는 DB 트랜잭션 실패 시 해당 요청이 생성한 파일과 부분 파일을 정리하고 DB 변경을 롤백한다.
- 성공한 요청의 파일과 메타데이터 및 기존 파일을 보존하며 기존 API 계약과 파일 검증을 유지한다.
- 파일의 요청별 소유권을 확보하고 트랜잭션 완료 시점에 정리한다. 정리 실패가 원래 실패를 감추지 않게 하고 원인과 한계를 확인할 수 있게 한다.
- 트랜잭션 완료 상태가 `UNKNOWN`이면 DB 결과가 불명확하므로 파일을 임의 삭제하지 않고 그 한계를 기록한다.

## 제외 범위

- 기존 고아 파일 일괄 삭제 및 프로세스 강제 종료 등의 복구 보장.
- 저장소 교체·클라우드 배포, 파일 내용 보안 검사, DB 구조 및 인증·인가 변경.

## 요구사항·API·ERD

- 실제 구현과 검증 결과에 맞춰 관련 요구사항과 API 문서를 필요한 범위에서 반영한다. 요청·응답과 오류 계약은 유지한다.
- DB 스키마 변경이 없으므로 ERD 변경은 필요하지 않다.

## 검증 계획

- 생성·수정 각각에 대해 여러 파일 중 후속 파일 검증 실패 및 부분 전송 실패를 재현하고 이미 저장된 파일과 부분 파일의 정리를 확인한다.
- 파일 저장 후 DB flush 또는 실제 트랜잭션 commit 실패를 검증하고, 트랜잭션 종료 후 DB와 파일을 별도로 조회한다. 기존 파일 보존과 성공한 요청의 파일·메타데이터 유지도 확인한다.
- 정리 실패가 원래 오류를 감추지 않고 다른 파일의 정리를 방해하지 않는지 확인하고 한계를 기록한다.
- 관련 Controller·Service·Repository 및 인증부터 DB·파일까지 통합 흐름을 검증한다. 테스트 DB와 임시 파일 경로는 격리하고 정리한다.
- 전체 `./gradlew test`를 실행하고 범위·결과 및 미검증 사항을 PR 또는 devlog에 기록한다.
